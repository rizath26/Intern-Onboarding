Deliverable 2: My Daily Feynman Checks
Day 1 – System Boundary

A system boundary tells us what belongs to a system and what is outside it. It is similar to a house boundary that separates our property from the outside area. When designing software, we need to know which parts we are responsible for and which parts belong to other systems. If we do not define this properly, we might miss important requirements or make the design more complicated than necessary.

Day 2 – API

An API is like a waiter in a restaurant. We tell the waiter what we need, and the waiter communicates with the kitchen and brings us the result. In the same way, an application sends a request through an API and receives a response. If the request is incorrect or something goes wrong, the API may return an error instead of the expected result.

Day 3 – Reliability

Reliability means that a system can continue doing its job correctly when people need it. It is like a bus service that people depend on to get to work every day. If the service stops whenever one problem occurs, people cannot depend on it. In software, we can improve reliability by handling errors properly, monitoring the system, and preparing for failures.

Day 4 – Cache

A cache is a place where frequently used information is stored temporarily so it can be accessed faster. It is like keeping the books you use most often on your desk instead of going to the library every time. Caching can make applications faster and reduce the workload on a database. However, if the cached information is not updated properly, users might see old information.

Day 5 – Specification

A specification explains what a software component is expected to do. It is like a recipe that tells us what ingredients we need and how to prepare a meal. In software, it explains what information a component receives, what result it should return, and what should happen when something goes wrong. If the specification is unclear, developers might build something different from what was expected.
